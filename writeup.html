The project

Bunbetsu in one sentence

Bunbetsu is an intelligent waste-management and spatial-planning platform for college festivals and campus events. It turns an event description and a campus map into a pre-event waste and infrastructure plan.

PredictEstimate total waste and its Food, Plastic, Paper, Glass, and Others composition.
PlaceRecommend on-site and roadside bins with map coordinates, streams, and emptying requirements.
ConnectBuild a campus pedestrian graph and identify important corridors between event zones.
ExplainShow assumptions, ranges, warnings, and stage diagnostics instead of hiding uncertainty.

The project was built for the AWS Build Bharat Hackathon under the Waste and Energy theme.

Why this matters

College festivals are temporary cities

For a few days, a campus may receive thousands of visitors. Food stalls, concerts, sports activities, exhibitions, workshops, and registration areas all generate different waste profiles. Yet waste planning often begins only after the event has started.

Organizers may not know how much waste to expect, how many bins are needed, where bins should go, or which pedestrian corridors will carry the most movement. This can produce overflowing bins, poor segregation, unnecessary collection trips, and bins in places where people rarely walk.

The core problem

  1. Too few bins in high-footfall areas.
  2. Too many bins in low-demand areas.
  3. Poor separation between recyclable and disposable waste.
  4. Bins placed away from the routes people actually use.
  5. No estimate of collection frequency or emptying requirements.
  6. No location-wise understanding of event waste.
There was another important constraint: a new college festival rarely has a clean, event-specific historical dataset ready for machine-learning training. Waiting for perfect data would mean waiting before building the solution.

That led us to an evidence-backed mathematical baseline: transparent enough to audit today, and structured enough to improve with real event data tomorrow.

The answer

From prediction to placement

Bunbetsu combines four connected planning capabilities:

Waste prediction

Estimate total waste, uncertainty ranges, composition, and location-wise contributions.

On-location bins

Convert waste into bin demand and place bins around event-zone boundaries.

Pedestrian routes

Build a walking network from OpenStreetMap and score important corridors.

Road-bin planning

Use route popularity, influence radii, and waste streams to recommend roadside stations.

Entry-gate planning

Require an in-campus gate and include it as an origin in route analysis.

Partial results

Keep valid waste and bin results available even when external route data fails.

The complete operation is exposed through POST /api/planning/plan. The backend executes the stages directly in Python and returns results, warnings, assumptions, and diagnostics together.

Inside the engine

Technical implementation

One request keeps the plan synchronized

The frontend sends event details, campus geometry, the entry gate, and active event locations through one unified planning request.

const payload = {
  fest_name: eventDetails.festName.trim(),
  total_footfall: eventDetails.expectedFootfall,
  duration_days: eventDetails.durationDays,
  campus_state: campus.state.trim(),
  campus_boundary: campus.geometry,
  entry_gate: {
    id: entryGate.id,
    name: entryGate.name,
    coordinates: entryGate.coordinates,
  },
  locations: locations.map((location) => ({
    id: location.id,
    name: location.name.trim(),
    area: location.area,
    activities: location.activities,
    geometry: location.geometry,
    center: location.center,
  })),
};

The client lives in frontend/src/services/planningApi.ts. The server endpoint is coordinated by backend/planning/planner_service.py.

Waste prediction

The core model is deterministic and range-based:

W = F × D × R × I
  • F: expected daily footfall.
  • D: event duration in days.
  • R: CPCB baseline waste rate in kg/person/day.
  • I: weighted activity intensity.

Attendee-days are calculated once as F × D, and low, central, and high intensity values produce the uncertainty range.

attendee_days = inputs.total_footfall * inputs.duration_days

waste = Range(
    attendee_days * baseline_rate * intensity.low,
    attendee_days * baseline_rate * intensity.central,
    attendee_days * baseline_rate * intensity.high,
)

Activity and location weighting

Activity weights describe relative contribution, not attendance estimates:

ACTIVITY_WEIGHTS = {
    "Food Stalls": 5,
    "Music Concert": 4,
    "Performing Arts": 3,
    "Literary & Fine Arts": 2,
    "Sports": 1,
    "Hackathon": 1,
}

Location waste is allocated using each location's sum of activity weights. Area remains spatial metadata and is not used as a direct waste multiplier.

share = location_activity_weight / total_activity_weight
location_waste = total_waste * share

Mass to bin demand

Category masses are converted into estimated volume using material densities:

V = Σ (Mi / ρi)

Bunbetsu uses 100-litre bins with an 80% usable fill fraction, giving 80 litres per filling turn:

Cusable = 100 × 0.80 = 80 litres

Daily bin demand is then:

N = ⌈ Vdaily / 80 ⌉

Food and Others form the Disposable stream. Plastic, Paper, and Glass form the Recyclable stream.

Perimeter-constrained placement

Physical placement is constrained by the configured 25-metre spacing policy:

M = ⌊ P / d ⌋

Here, P is the approximate location perimeter and d is the spacing policy. When capacity demand exceeds physical perimeter capacity, bins are allocated between streams with a deterministic largest-remainder method, and extra emptying turns are calculated.

Coordinates are sampled along an inward-offset exterior boundary and validated so the returned points remain inside the event polygon.

Pedestrian graph and route scoring

The routing pipeline retrieves eligible OSM ways, projects them into local metres, clips them to the campus boundary, and constructs a NetworkX graph. Activity locations are connected by snapping to nearby mapped edges. Connectors are marked separately from mapped paths and can be flagged if they cross buildings or barriers.

For each connected pair, the scorer considers the shortest path and bounded alternative loopless paths. This is Yen-style k-shortest-path behavior implemented with NetworkX's weighted simple-path generator, with limits on path count and additional distance.

Pk = e-Δk / λ / Σj e-Δj / λ

Pair attraction uses a symmetric geometric mean:

Aab = √(wa × wb)

Path contributions accumulate on mapped road segments and are normalized to [0, 1]. These are modeled relative importance scores, not sensor-measured footfall.

Campus result ranking

Nominatim can return a university, a department building, a nearby road, or another similarly named place. Bunbetsu ranks candidates using educational OSM classes, university/college/campus types, campus-related keywords, and polygon availability. State information is taken from structured address fields such as state, province, and region.

What made it difficult

Challenges and solutions

1. No event-waste dataset

A reliable supervised model would need historical footfall, event type, duration, location, waste category, and collection data. That dataset was not available at the start.

Solution

We researched credible references and built a transparent baseline using CPCB state and UT rates, activity weights, composition priors, intensity bands, and low/central/high ranges. The model records assumptions and can later be calibrated with real events.

2. Bin counts had to become map actions

A number alone does not tell an organizer where to put infrastructure. The model also needed to handle waste streams, polygon sizes, perimeter limits, and emptying frequency.

Solution

We convert mass into volume, calculate capacity demand, apply a 25-metre spacing policy, sample inward-offset polygon boundaries, preserve exact coordinates, and report shortfalls instead of inventing unrealistic placements.

3. The entry gate changes movement

Pedestrian movement needs an origin as well as event destinations. The entry gate is also a likely collection and waste concentration point.

Solution

The UI requires the organizer to place a gate inside the campus. It is validated geographically and included as a Point location in the route graph.

4. One shortest path is not enough

Visitors may use several routes because of crowding, barriers, accessibility, or convenience. Scoring only one route could miss important corridors.

Solution

We evaluate bounded alternative paths, apply exponential distance decay, and build a popularity index for mapped road segments. Popular corridors become stronger roadside-bin candidates.

5. Campus roads were not already available

Every college has a different boundary and pedestrian layout, and there was no single project-specific map dataset.

Solution

Nominatim supplies campus search and geometry. Overpass supplies local walkable ways, buildings, and barriers. Local processing builds a campus-specific graph, with caching and bounded retries.

6. OpenStreetMap returned multiple matches

A name can match the university, a building, a road, or a nearby place. Choosing the first response would be unreliable.

Solution

We rank results using OSM tags, education-related classes, campus keywords, and polygon geometry. Structured address fields provide a safer state lookup than parsing display text alone.

7. Geometry could break physical decisions

Invalid polygons, narrow zones, disconnected components, and rounding near boundaries can create unsafe or impossible bin coordinates.

Solution

GeoJSON is validated at the API boundary. Shapely and browser utilities check ring closure, positive area, containment, intersections, inward buffers, and final returned coordinates.

8. External services can fail

Nominatim and Overpass can time out, rate-limit requests, return no paths, or temporarily become unavailable.

Solution

The system uses timeouts, bounded retries, temporary caching, explicit errors, non-blocking route warnings, and partial pipeline responses.

Testing, deployment, and results

Testing

Backend tests cover API validation, campus search, waste calculations, unified planning, stable IDs, polygon and MultiPolygon placement, Point handling, OSM filtering, graph construction, connectors, and route scoring.

Frontend tests cover the unified request contract, response mapping, duplicate-name and missing-state validation, heatmaps, polygon drawing and erasing, road-bin integration, location-aware recommendations, entry-gate behavior, campus isolation, dashboard navigation, and empty states.

python -m pytest -c backend/pytest.ini backend
npm --prefix frontend run lint
npm --prefix frontend run build
npm --prefix frontend test

Deployment

For local development, install Python dependencies from backend/requirements.txt, start FastAPI on port 8000, then run the Vite frontend on port 3000. Vite proxies /api requests to the backend.

pip install -r backend/requirements.txt
uvicorn server:app --app-dir backend --reload --port 8000

cd frontend
npm install
npm run dev

Production deployment should add HTTPS, specific CORS origins, persistent caching, rate limiting, monitoring, real authentication, database-backed event plans, and background jobs for large routing requests.

What comes next

Key learnings and future scope

Key learnings

Start before perfect dataResearch-backed assumptions and a transparent baseline can create useful value while real data is still being collected.
Prediction needs actionA waste estimate becomes more useful when connected to bins, locations, routes, emptying, and warnings.
Show uncertaintyLow, central, and high values are more honest and operationally useful than one falsely precise number.
Design for failurePartial results and diagnostics are essential when map data or public services are incomplete.

Future scope

Existing campus bins

Import permanent bin coordinates, capacities, streams, conditions, and collection schedules so the system recommends only extra festival bins.

Learn from every event

Capture actual collected waste, fill times, overflow incidents, contamination, and footfall to calibrate campus-specific models.

Real-time fill monitoring

Use sensors to alert staff about nearly full bins, high-demand corridors, and contamination.

Collection routing

Turn the same pedestrian graph into an operational route for collection teams, prioritizing full bins and short travel.

Richer inputs

Add hourly footfall, schedules, ticket scans, crowd density, venue capacity, and peak-hour forecasts.

Safety and accessibility

Include emergency lanes, accessible paths, slopes, stairs, entrances, service roads, and temporary barriers.

More waste streams

Support compostables, e-waste, sanitary waste, glass-specific collection, cooking oil, and reusable-cup systems.

Institutional planning

Manage multiple campuses, reuse event templates, compare festivals, and maintain long-term campus profiles.

Exports and reporting

Generate PDFs, CSV schedules, printable maps, staff assignments, diversion rates, and estimated emissions savings.

Explainable learning

Keep the deterministic model as a baseline while adding campus-specific corrections with confidence intervals.

Weather awareness

Account for rain, temperature, outdoor activity, seasonal food demand, and temporary route closures.

Sustainability metrics

Measure landfill diversion, recycling, compost recovery, collection distance, avoided emissions, and overflow reduction.

Planning cleaner events starts before the event begins.

Bunbetsu turns festival waste planning from a reactive task into a pre-event workflow. It combines an explainable waste model, a geographic interface, polygon-aware bin placement, OpenStreetMap pedestrian data, route popularity scoring, and roadside-bin recommendations.

The project began with a practical constraint: there was no perfect festival dataset. Instead of stopping, we built a transparent baseline with CPCB references, documented assumptions, and uncertainty ranges. As real event data arrives, the same architecture can grow into a sensor-driven, campus-specific sustainability system.
